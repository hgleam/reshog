# メモリ検出ロジック（算出仕様）

reshog の中核。「なぜ物理フットプリントでランクするか」と「GPU/Metal 常駐の判定式」を実コード
（`src/reshog/models.py`・`src/reshog/parse.py`）を根拠に記す。

## 物理フットプリント vs RSS

| 指標 | 出所 | 特性 |
|------|------|------|
| MEM（物理フットプリント） | `top -o mem` の MEM 列 | Activity モニタ「メモリ」列相当。GPU 共有メモリを含む |
| psRSS | `ps -o rss` | Metal/MPS（GPU 共有＝ユニファイドメモリ）を**数えない**ため過小に出る |

ランク付けは常に **MEM（物理フットプリント）降順**（top の並びをそのまま保つ）。

## GPU/Metal 常駐の判定式

`Process.hidden_gpu`（`models.py`）。ps の RSS に現れない GPU/Metal 常駐メモリを抱えているかを判定する。

```
hidden_gpu = (mem_mb >= HIDDEN_GPU_MIN_MB) and (mem_mb > rss_mb * HIDDEN_GPU_RSS_RATIO)
```

| 定数 | 値 | 意味 |
|------|-----|------|
| `HIDDEN_GPU_MIN_MB` | `2000` | この MB 以上の物理フットプリントを持つプロセスのみ対象（小物を除外） |
| `HIDDEN_GPU_RSS_RATIO` | `4` | MEM が psRSS の 4 倍を**超える**とき「小さく見えるのに巨大」とみなす |

- 境界: MEM がちょうど RSS の 4 倍（`==`）は **False**（`>` のため）。4 倍を少しでも超えると True。
- 例: ComfyUI（MEM 32G / RSS 26M）・llama-server（MEM 6.6G / RSS 12M）は True。
  仮想マシン（MEM 7.9G / RSS 2.6G）は比が約 3 倍で False。

True のプロセスは表・JSON で `⚠ GPU/Metal常駐(psに出ない)`（`hidden_gpu: true`）として印付けされる。

## アプリ単位の合算とその限界（`--group`）

`ProcessGroup.total_mb` は所属プロセスの MEM を**単純合算**する（`models.py`）。

物理フットプリントはクリーンな共有ページの二重計上を避けるが、プロセス間で共有する
dirty page（IPC 共有メモリ・Chromium のプロセス間共有アリーナ・GPU 共有サーフェス等）は
**各プロセスの footprint にそれぞれ計上されうる**。したがってアプリ単位の合計は
**上限寄りの推定値**であり、実際に解放される物理メモリはこれより小さいことがある。

分散して埋もれているアプリを見つける（＝順位付けする）用途には十分だが、
「このアプリを落とせば N GB 空く」と読むのは誤り。実際の空き変化は前後の PhysMem で確認する。

## メモリ値の解析（`parse.py`）

### `parse_mem_to_mb(value)`

top の MEM 文字列を MB(float) に変換。末尾の増減記号（`+`/`-`、前サンプルからの変化）は無視する。

| 単位 | 係数（→ MB） |
|------|-------------|
| `G` | ×1024 |
| `M` | ×1 |
| `K` | ×1/1024 |
| `B` | ×1/(1024×1024) |
| （無単位） | ×1 |

解釈できない文字列は `ValueError`。正規表現 `^([0-9]+(?:\.[0-9]+)?)([GMKB]?)$`。

### `parse_top_processes(output)`

`PID` で始まるヘッダ行以降のみを対象に `(pid, mem_mb, cpu)` を抽出。3 列未満・PID が数値でない行、
MEM がパース不能な行はスキップ。CPU がパース不能なら 0.0。top の並びを保つ。

**出力には 2 サンプル分の表が入るため、`PID` ヘッダを見つけるたびに収集済みの行を捨て、
最後の表だけを採る。** 継ぎ足すと同じ PID が 2 回現れ、件数も `--group` の合計も倍になる。

## CPU の取得（`collect.py` / `parse.py`）

`top` は **1 サンプル目の %CPU を必ず 0.0 で返す**（前回サンプルとの差分が取れないため）。
1 サンプルしか取らない実装では `%CPU` 列が常に 0 になる。`TOP_SAMPLES = 2` で 2 サンプル取り、
`parse_top_processes` が 2 つ目だけを読む。実測で 1 回の実行に約 1.3 秒余分にかかるが、
表示している %CPU が常に嘘であるより待ち時間のほうが害が小さい。

ヘッダ値（`PhysMem` / `Load Avg` / `CPU usage`）も同じ理由で**最後の出現**を採る
（`_last_header_value`）。最初の出現を採ると 1 サンプル目＝古い値になる。

- `parse_load_average(output)` → `"9.79, 10.32, 14.15"`（1 / 5 / 15 分平均）。
  **3 つを並べて見ることに意味がある**。1 分だけ高いなら一過性、3 つとも高いなら定常的な詰まり。
- `parse_cpu_usage(output)` → `"22.3% user, 24.31% sys, 53.65% idle"`。
  sys が user を大きく上回るときは、個々のプロセスの計算ではなく**カーネル側の処理**
  （プロセス生成の嵐・I/O・ページング）を疑う手がかりになる。

### アプリ単位の CPU 合計（`ProcessGroup.total_cpu`）

メモリと同じく members から導出する（冗長な列は持たない）。1 プロセスずつ見ると数 % でも、
同じものが何十個も動いていれば合計は跳ねる。**`--group` ではメモリ順で見ているときも
合計 CPU 列を常に出す**（埋もれている消費に気づけるように）。

### 短命プロセスの集計（`report.build_churn` / `churn.py`）

`top` の 2 サンプルの間に生まれて終わるプロセスは、CPU の一覧に一度も出ない。claude の
セッションがフックを起動し続ける・テストを並列で流すといった負荷は、1 本ずつは一瞬で終わるので、
負荷平均が高いのに一覧には WindowServer くらいしか出ない、という見え方になる。

- `--sort cpu` のときだけ数える（`cli._render_view`）。`CHURN_SECONDS` の間、
  `CHURN_POLL_SECONDS` ごとに `ps` を撮り、数え始めのスナップショットに無かった PID を集める。
  秒数は実際に数えた時間で割る（負荷が高いと ps 自体が遅れて、設定より長くなる）。
- 束ねる先は**数え始めから動いていた祖先**（`churn.attribute`）。すぐ上の親で束ねると、
  フックの bash → python のように間の親も短命なときに「bash が bash を生んだ」としか分からない。
- 数え始めに写った親が途中で終わっていたら（最後のサンプルに居ない）、さらに上へ辿る。
  1 秒に 100 本生まれる状況では数え始めにも短命な bash が必ず写り、そこで止めると起動元が割れる。
- 親が先に終わった子は launchd（`LAUNCHD_PID`）に付け替わって見えるので、起動元を
  「launchd(親が先に終わったものを含む)」と表記する。
- 数え始めの ps が読めなければ数えない（`None`）。空と比べると全プロセスが新しく見えるため。
  表は「数えられませんでした」、JSON は `churn: null`（数えていない memhog はキー自体を出さない）。
- 自分が叩いた ps（祖先が自分）は数えない。親がどのサンプルにも写らなかったものは
  `CHURN_UNKNOWN_PARENT` に入れて「(親不明)」と出し、本数からは落とさない。
- 本数は**下限**（ps を撮る間に生まれて終わったものは数えられない）。表示も「N 本以上」と書く。
- 表は起動元の上位 `CHURN_TOP_SOURCES` 件で、残りは「ほか N 起動元」の 1 行に足す
  （行の合計が見出しの本数と合うように）。中身は名前の多い順に `CHURN_TOP_CHILDREN` 個で、残りは「ほか N」（中身の合計が行の本数と合うように）。
- PJ は起動元にだけ付ける（`report._with_origins` を起動元のプロセスに掛ける。lsof は 1 回）。

### `format_mb(mb)`

表示整形。1024 以上なら `12.3G`、未満なら `512M`（四捨五入）。

## 表示上の強調（`render.py`）

- MEM（`--group` では合計 MEM）が `ALERT_MB = 8000` MB 以上の行は赤字で強調（大口消費の視認性）。
- `--sort cpu` のときは CPU（`--group` では合計 CPU）が `ALERT_CPU = 100.0`（= 1 コア分）
  以上の行を赤字で強調する。強調の基準は**並べた基準に合わせる**（メモリ順のまま CPU で
  赤くすると、順位と色が食い違って読めなくなる）。
- コマンドは 96 文字で末尾省略（`MAX_CMD = 96`）。
- **他プロセス由来の文字列（コマンド・アプリ名）は `rich.markup.escape` を通してから
  `console.print` する**。プロセス名は自分の意のままに付けられるので、`[bold red]` 等を
  含む argv があると表示が乗っ取られる（表のセルは `Text` なので元から解釈しない）。
- **フッタが提案するコマンドは「いま見ている並び順を再現するコマンド」にする**
  （`COMMAND_BY_SORT[order]`）。起動に使ったコマンド名をそのまま出すと、
  `memhog --sort cpu` で見ているのに `memhog --app X` を勧めることになり、
  開き直した画面の並びが変わる。表示は成立し実行もできる（並びが違うだけ）ので、
  指摘されるまで気づけない。
- **フッタが提案するコマンドは `shlex.quote` でクォートする**。そのままコピペされる前提の
  出力に、引用符やセミコロンを含むアプリ名がそのまま載ると、貼った側のシェルで別のコマンドが走る。
