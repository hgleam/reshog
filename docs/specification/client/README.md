# reshog — 依頼者向け仕様書

## 概要

macOS の**実メモリ（物理フットプリント）を最も食っているプロセスを特定して提示する**診断 CLI。

`ps aux` の RSS は Metal/MPS（Apple Silicon の GPU 共有＝ユニファイドメモリ）を数えないため、
ComfyUI 等の ML 系 Python は RSS 上「数十 MB」に見えるのに実際は数十 GB を常駐している。
reshog は Activity モニタ相当の物理フットプリント（`top` の MEM 列）でランク付けし、RSS との
乖離が大きいプロセスに `⚠ GPU/Metal常駐(psに出ない)` 印を付けて「小さく見えるのに実は巨大」を炙り出す。

また、Chromium 系ブラウザや MCP サーバはヘルパープロセスへ分散するため、1 プロセスずつの
ランキングには現れない。`--group` はこれを親子関係でアプリ単位に合算して可視化する。

同じ「分散して埋もれる」問題は CPU にもある。`--sort cpu` で CPU 順に切り替えられ、
`--group` と併せるとアプリ単位の CPU 合計が見える（1 プロセスずつ見ると数 % でも、
同じものが何十個も動いていれば合計は跳ねる）。

| 機能 | 説明 | 状態 |

| GPU/Metal 常駐の検出 | RSS に現れない GPU 共有メモリを抱えるプロセスに警告印 | ✅ 実装済み |
| アプリ単位の合算 | ヘルパープロセスを親子関係でたどりアプリ単位に合算（`--group`） | ✅ 実装済み |
| アプリの内訳表示 | `--group` の APP 名を指定して所属プロセスを一覧（`--app`） | ✅ 実装済み |
| コマンドフィルタ | フルコマンドへの部分一致（大小無視）で絞り込み（`-g`） | ✅ 実装済み |
| JSON 出力 | 機械可読な JSON（通知連携・定期実行向け）（`--json`） | ✅ 実装済み |
| 監視モード | 指定秒間隔で画面を更新し続ける（`--watch`） | ✅ 実装済み |
| プロセス停止 | 一覧から PID を選んで停止（既定で確認、不可逆）（`--kill`） | ✅ 実装済み |
| システムメモリ表示 | PhysMem・Swap・空き割合を併記 | ✅ 実装済み |
| CPU 順表示 | CPU 使用率の降順で一覧（`cpuhog` / `--sort cpu`） | ✅ 実装済み |
| 2 つのコマンド | `memhog`（実メモリ順）と `cpuhog`（CPU 順）。既定の並び順だけが違う同一 CLI | ✅ 実装済み |
| アプリ単位の CPU 合計 | `--group` に合計 CPU 列を常に併記（分散して埋もれる消費を可視化） | ✅ 実装済み |
| システム CPU 表示 | Load Avg（1/5/15分）と user / sys / idle の内訳を併記 | ✅ 実装済み |
| 短命プロセスの出どころ | CPU 順（`cpuhog` / `--sort cpu`）のときだけ、約 3 秒間に新しく生まれたプロセスを数え、それを生んでいる起動元（数え始めから動いていた親。claude のセッション・pytest・CI のランナー等）ごとに本数・PJ・主な中身を表の末尾に出す。数秒で終わるプロセスは CPU の一覧に一度も出ないので、負荷平均が高いのに一覧が静かなときの原因はここで見える。本数は下限（ps を撮る間に生まれて終わったものは数えられない）。実行はその分長くなる。`--json` では `churn` に入る。ps が読めず数えられなかったときは「数えられませんでした」と出す（0 本とは出さない） | ✅ 実装済み |
| 短命プロセスの記録と増加 | `cpuhog --record` で短命プロセスを数え、出どころ（`PJ:起動元`）ごと・中身の名前ごとの毎秒の本数を記録へ 1 行足す。`cpuhog --trend` で記録を読み、直近 1 日の平均がその前の 7 日の平均より増えたもの（毎秒 1 本以上で 1.5 倍を超えたもの）を出す。1 本ずつは軽いもの（フック・statusline・プラグイン等）が積み上がって負荷になるのを、種類を問わず増え始めで見つけるため。直近と過去のどちらかに記録が無ければ「比べられません」と出す（「増えていない」とは出さない）。数えられなかった回は記録しない。読めない行（壊れた行・時刻にタイムゾーンが無い行・本数が数でない行）は比べずに「読めなかった行が N 行」と件数を出す。時刻が今より先の記録（時計のずれ）も比べずに件数を出す。記録へ書けなければ理由と置き場の変え方を出して終える。`--record` / `--trend` はほかのオプション（`--grep`・`-n` 等を含む）と一緒には使えない毎日の自動実行と通知はまだ無い（手で回して要るか確かめてから足す） | ✅ 実装済み |
| 由来プロジェクト表示 | プロセス別の表に PJ 列（git リポ名 / `launchd:<ジョブ名>` / `-`） | ✅ 実装済み |
| PJ 別の合計 | 全プロセスを PJ 列と同じ判定でプロジェクトごとに合算し順位付け（`--project`）。PJ 不明は順位に入れず別に合計 | ✅ 実装済み |
| OS のプロセスの説明 | WindowServer・launchd・Spotlight（mds 等）・仮想マシン・XprotectService に「何のためのものか・止めてよいか」を添える。止めてはいけないもの（WindowServer・launchd）は停止の案内を出さず、`--kill` で選ぶと警告する。Spotlight は止めてよいがすぐ起動し直し、止めるには管理者権限が要る。仮想マシンは起動元のアプリを終了する（強制終了すると中の作業が失われうる）。XprotectService（マルウェア検査）は止めず、署名の無い実行ファイルが検査に回るのが原因なので、端末アプリをデベロッパツールに登録して起動し直すよう案内し、効いたかを確かめるコマンド（syspolicyd の 1 分あたりの検査件数）を添える | ✅ 実装済み |
| ローカル LLM の休止状態 | llama-server の行に「💤 休止中(14:21 から)」「▶ 稼働中(14:14 に復帰)」。`--sleep-idle-seconds` の休止はプロセスが同じままなので「起動」列は変わらず、この表示で「いまモデルを掴んでいるか・いつから」を示す | ✅ 実装済み |
| 開始時刻表示 | プロセス別の表に起動列（`MM-DD HH:MM`、ローカル時刻） | ✅ 実装済み |

## 利用方法

```bash
memhog                 # 実メモリ上位15件
memhog -n 30           # 上位30件
cpuhog                 # CPU 使用率の降順（= memhog --sort cpu）。末尾に短命プロセスの出どころ（約 3 秒かかる）
cpuhog --group         # アプリ単位の CPU 合計（分散して埋もれる消費を炙り出す）
memhog --sort cpu      # cpuhog と同じ。どちらから入っても同じ CLI
memhog -g python       # フルコマンドに "python" を含むものだけ
memhog --group         # アプリ単位に合算して表示（`-n` はグループ数、`-g` は合算前に適用）
memhog --app ixBrowser # そのアプリに属するプロセスの内訳（--group の APP 名を指定）
memhog --project       # プロジェクトごとの合計（どの PJ が一番食っているか。`-n` は PJ 数）
memhog --json          # 機械可読 JSON
memhog --watch 2       # 2秒ごとに更新し続ける監視モード（Ctrl-C で終了）
memhog --kill          # 一覧から PID を選んで停止（既定で確認、不可逆操作）
memhog --kill --force  # SIGKILL で停止
memhog --kill -y       # 確認を省略して停止
memhog --version       # バージョン表示
cpuhog --record        # 短命プロセスを数えて記録へ 1 行足す（約 3 秒。日をまたいで何度か回す）
cpuhog --trend         # 記録を読み、直近 1 日に前の 7 日より増えた出どころ・中身の名前を出す
```

セットアップ手順は [開発者向け仕様書](../develop/README.md) を参照。

| 変数名 | 用途 | 必須 |
|--------|------|------|
| `RESHOG_CHURN_LOG` | `--record` が書き `--trend` が読む記録の置き場。無ければ `~/.local/state/reshog/churn.jsonl` | 任意 |

## 制約・受け入れ基準

- **macOS 専用**。`top` / `ps` / `sysctl` / `memory_pressure` に依存する（Linux では動作しない）。
- **`top` を 2 サンプル取る**（1 サンプル目の %CPU は前回サンプルとの差分が無く必ず 0.0 になるため）。
  そのぶん 1 回の実行に約 1.3 秒余分にかかる。表示している %CPU が常に嘘であるより、
  待ち時間のほうが害が小さいと判断した。
- **`memhog` と `cpuhog` は同一の CLI**。違いは `--sort` の既定値だけで、オプション一式は同じ。
  どちらのコマンドからでも `--sort` で他方の並び順に切り替えられる。
- `--sort` は `mem` か `cpu`（既定は `memhog` なら `mem`、`cpuhog` なら `cpu`）。**並べ替えは `top` 側の並び順ごと切り替える**。
  取得後に並べ替えるだけでは、母集団が「メモリ上位 N 件」に固定され CPU 上位が入らない。
- %CPU は**直近サンプル間の使用率**で、100% = 1 コア分。コア数ぶんまで 100% を超えうる。
- 外部コマンドが失敗しても例外は投げず、取得できた範囲で表示する（空欄になる）。
- `--kill` は不可逆操作。既定で確認プロンプトを出し、PID ≤ 1・自分自身は停止不可。
- **launchd の常駐ジョブ**（`launchctl list` に載っているもの。GUI アプリの自動ラベル `application.*` は除く）は、
  `KeepAlive` なら kill しても launchd がすぐ別の PID で起動し直す。表の下の停止案内は、そのプロセスが
  ジョブなら `kill <PID>` ではなく `launchctl bootout gui/<uid>/<ジョブ名>`（sudo で実行したときは `system/<ジョブ名>`）を
  出す（戻すときは `launchctl bootstrap <ドメイン> <plist のパス>`）。OS のエージェント（`com.apple.*`）には bootout を勧めず `kill` を案内する
  （bootout はジョブを台帳から外すので、再ログインまで機能が欠けうる）。`--kill` でジョブを選ぶと、確認の前に同じ警告とコマンドを出す（確認すれば従来どおり送る）。
  PJ 列がリポ名でもジョブであることはある（例: tokyo-calendar の llama-server）ので、PJ 列とは別に判定する。
- `--watch` は `--json` / `--kill` と併用できない。データを集め終えてから画面を書き換えるので、
  全プロセスを走査する `--group` / `--project` でも、待っている間は前回の表示が残る。
- `--group` は `--kill` / `--app` と併用できない（合計か内訳かを選ぶ）。`--app` は `--kill` と併用可。
- **PJ 列の判定順**: ①作業ディレクトリを含む git リポ名（worktree は元のリポ名に寄せる）
  ②リポの外で動く launchd の常駐ジョブならジョブ名（`launchd:` を付けて区別。GUI アプリに
  自動で付く `application.*` は除く）③どちらも無ければ `-`。GUI アプリ・XPC・Docker の VM のように
  作業ディレクトリが `/` のもの、権限が無くて読めない root のプロセスは `-` になる。
- PJ 列・起動列は**プロセス別の表**（通常・`--app`）だけに出す。`--group` はアプリの中に
  別プロジェクトのプロセスが混ざるため 1 つの値にまとめられず、出さない。
- 表示分のプロセスに対して `lsof`・`launchctl list`・`ps` を 1 回ずつ追加で叩く（実測 約 0.2 秒）。
- **llama-server の休止状態**は、自分のマシンで待ち受けているものだけ `/props` に問い合わせて決める（最大 1 秒待つ。
  読むだけで休止中のサーバーを起こさない）。その状態になった時刻は、launchd のジョブなら `launchctl print` で
  分かるログの末尾 2 MB から、最後の `entering / exiting sleeping state` 行の「起動からの経過」を開始時刻に足して出す。
  ログの場所が分からない・今回の起動に出入りが無い・直近の出入りが読んだ末尾 2 MB より前にある・
  ログと `/props` が食い違うときは時刻を出さない（推測しない）。時刻は分まで表示するので、境界で ±1 分ずれうる。
  他のマシンの llama-server には問い合わせない（`::1` で待ち受けていれば `[::1]` へ）。環境のプロキシ設定は通さない。
  待ち受け先は コマンド行の `--host`/`--port` から決める（環境変数 `LLAMA_ARG_HOST`/`LLAMA_ARG_PORT` での指定は読まない）。
  応答が無いときは 1 本あたり最大 1 秒待つ（`--watch` の更新はそのぶん遅れる）。
- `--project` は全プロセスの作業ディレクトリを 1 回の `lsof` で引く（約 950 プロセスで 0.9〜2 秒）。
  全プロセスを走査する点は `--group` と同じで、全体の所要時間は `--group` とほぼ同じ。
- `--project` の PJ 不明（GUI アプリ・root のプロセス等）は順位に入れず、表の下に合計だけを出す。
  順位に入れると、まとめて 1 位に居座って PJ どうしの比較が見えなくなるため。
- `--project` は `--group` / `--app` / `--kill` と併用できない。`-g`（合算前に適用）・`--sort`・
  `--json`・`--watch` とは併用できる。
- `--group` の合計は**上限寄りの推定値**。プロセス間で共有する dirty page が重複計上されうるため、
  「落とせばこの分だけ空く」とは読めない（順位付けの指標として使う）。
- `--group` に `-g` を併せると、一致したプロセスだけの**部分合計**になる（見出しにその旨を表示する）。
- `--group` の合算単位はプロセスの親子関係。シェル・端末・多重化ツール（zsh / tmux 等）は
  「器」として素通りし、その配下のコマンドを 1 アプリとして数える。配下に実体が無い場合
  （アイドルなシェルだけ）は、そのシェル自身が 1 グループとして現れる。
- 権限不足（他ユーザーのプロセス等）の停止は失敗し、その旨を表示する。
