# devlog の書き方

仕様書は「結果」、`docs/devlog.md` は「**過程（壁打ちで何をどう練り直したか・変えた判断・理由）**」を
残す。両者は別物で、仕様書だけでは設計のブラッシュアップが追えないため両方残す。

## いつ書くか

作業アーク（機能・セッション）の**完了時**。コミット毎ではない。小修正の逐一記録は不要。

## 何を書くか

各エントリに 背景・壁打ち / 設計のブラッシュアップ（当初案→変更→理由）/ 実装(PR) / 決定・未決 を書く。

## 失敗・行き止まり・ハマった罠

「①当初案（もっともらしい）→ ②外れた具体（実測値・実出力）→ ③根本原因 → ④教訓（一般化）」で残す。
設計の却下案だけでなく、実装中に黙って外れたバグ・罠（例: 外部ライブラリのエラー判定・型・非同期の
落とし穴）も、教訓が一般化できるものは含める。後で外部発信（技術記事・失敗事例）の題材にもなるため、
**固有名・秘匿情報は入れず一般化した教訓の形**で書く。

## 避けること

- 作業アーク完了時に devlog を書かない（過程が失われ「なぜこの形か」を辿れなくなる）
- 失敗を「直して終わり」にして残さない（もっともらしく外した実装・罠は教訓ごと残す）
